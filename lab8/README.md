## Часть 1 — Кейс и боль компании

> *«Любое достаточно продвинутое согласие на обработку ПДн неотличимо от текста, который никто не читал».*  
> *— Артур Кларк, если бы работал в медтехе*

За контекст компании возьмем маленький медтех-стартап. **Проект** — медицинское мобильное приложение (функционал опустим, он не столь важен). Проект выходит на этап MVP, на сервере запущены 3 микросервиса: аутентификация, биллинг для оформления подписок и бэкенд сервис приложения. Есть мобильное приложение и сайт с информацией.

**Команда** состоит из 3 человек:
 - Фронтендер — на нем сайт и мобильное приложение
 - Бэкендер — весь бэк сервисов. На нем же лежат функции devops`а
 - Юрист (он же `запасной` разработчик) — В основном отвечает за юридические документы, согласия, ПДн. Иногда, при надобности, подключается к процессу разработки (В общем, и швец и жнец).

Главной болью стартапа, особенно в медтехе, как оказалось, является не нехватка людей для разработки и даже не отсутствие денег на развитие, а великий и ужасный **152-ФЗ**.

Поэтому я придумал процесс автоматизации с пафосным названием **"Страж персональных данных"**, который должен помогать юристу и разработчикам отслеживать собираемые данные и их статус в согласиях, а также ловить потенциальные утечки в коде.

**Триггер:** новый PR в GitHub. Workflow ищет новые файлы миграций sql-builder`a, новые зависимости и запускает статические проверки кода на поиск потенциальных уязвимостей. Затем параллельно запускаются две ветки:
 - Агент проверяет файлы миграций на предмет появления новых полей в БД, которые в теории могут являться персональными данными и ищет куда они могут передаваться, потом формирует отчет с уровнем риска PR.  
 - Второй агент запускает security audit по результату статических проверок, чтобы подтвердить или опровергнуть наличие уязвимостей связанных с персональными данными, формирует отчет о проверке.

После работы агентов отчеты склеиваются и публикуются в комментарий к реквесту с опциональным пингом юриста (и меткой с требованием юридической проверки) и блоком мерджа при высоком уровне риска. В итоговом отчете содержатся новые поля БД, которые являются персональными данными, предложения по правкам документов или аргументация почему эти данные не стоит добавлять и уровень риска (`low|mid|high`) по всему PR.

> Юрист больше не пишет в чат в пятницу в 23:40 «а мы это в согласии указывали?». Страж отвечает раньше, чем он успеет спросить, а главное, не обижается, когда его не читают. Наверное...

> (Хотя я бы лишний раз так не делал. А то мало ли восстание ИИ) 

## Часть 2 — Реализация workflow

![Полный пайплайн workflow](screenshots/1.png)

> Схема показывает исходный дизайн. Нижний блок («Ожидание решения → Одобрено / Нужны правки / Нет ответа») **не реализован**, реализованная часть заканчивается ветками Low / Medium / High.

Так workflow выглядит в n8n:

![Workflow PD Guard в n8n](screenshots/4.png)

- [✅] **Триггер.** Вебхук GitHub на открытие PR в `main` (`opened`, `reopened`) и на новый пуш в тот же PR (`synchronize`). Остальные события (метки, комментарии, закрытие) отбрасываются фильтром, иначе собственные метки Стража запускали бы проверку по кругу.
- [✅] **И AI, и не-AI шаги.** AI: юридический агент и агент разбора находок semgrep. Не-AI: нормализация события, фильтр по событию и ветке, получение списка файлов PR через GitHub API, классификация файлов по путям, статический скан (semgrep), объединение отчётов, публикация комментария, метки, статус-чек и создание задачи на правку реестра.
- [✅] **MCP-серверы.** (1) **GitHub MCP** (`github-mcp-server` 2.0.2) в режиме `--read-only` с наборами инструментов только `repos` и `pull_requests` и с fine-grained токеном на чтение одного репозитория. (2) **Filesystem MCP** (`@modelcontextprotocol/server-filesystem`) с каталогом юридических документов, смонтированным в контейнер только на чтение. Оба сервера работают по stdio, поэтому каждый обёрнут в `supergateway` (stdio → Streamable HTTP): MCP Client Tool в n8n подключается только по сети.
- [✅] **AI toolkit.** Имена в skill юридического агента написаны «по смыслу», у реальных MCP-серверов они другие, поэтому в начало System Message добавлена преамбула-словарь (сам файл skill не менялся):

  | Инструмент в skill | Что вызывается на самом деле | Вход |
  |---|---|---|
  | `get_pr_diff` | GitHub MCP `pull_request_read`, `method: get_diff` | owner, repo, номер PR |
  | `get_file_contents` | GitHub MCP `get_file_contents` | owner, repo, path, ref |
  | `read_legal_docs` | Filesystem MCP `list_directory` + `read_multiple_files` | путь `/docs`, список файлов |
  | `get_package_info` | n8n HTTP Request Tool → `registry.npmjs.org/<пакет>/latest` | package_name |

  ![Устройство юридического агента](screenshots/2.png)

  Агент разбора semgrep использует один инструмент: `get_file_contents` (semgrep без входа в аккаунт не отдаёт сниппеты кода, `lines: "requires login"`, поэтому агент читает файл сам).
- [✅] **Описанные skills.** Лежат в [`./skills`](./skills) и используются как System Message агентов: `pd-legal-review.md` (юридическая проверка) и `pd-security_audit.md` (разбор находок semgrep). В них порядок действий, правила определения риска, лимиты вызовов инструментов, защита от prompt injection и формат ответа (JSON).
- [✅] **Конкретный результат.**
  - Комментарий-отчёт в PR: что найдено, почему это ПДн, чего не хватает в документах, находки аудита утечек, предложения по правкам согласия и реестра.
  - Метка и статус-чек `pd-guard` по уровню риска: `high` → метка `legal-review:pending` и статус `pending`; `medium` → задача (issue) на правку реестра ПДн и зелёный статус; `low` → зелёный статус.

> Что из первоначальной идеи **не реализовано**: ожидание решения юриста (одобрено / нужны правки / нет ответа с пингами через 3 и 5 дней) и автоматический PR с правкой реестра. Для учебного проекта это слишком много: решение юриста принимается вручную, статус `pending` снимается вручную. Пинг юриста упоминанием в комментарии тоже не сделан.

## Часть 3 — Локальный запуск

### Что поднимается

Весь стенд описан одним [`docker-compose.yaml`](./stand/docker-compose.yaml) в каталоге [`stand/`](./stand):

| Сервис | Назначение | Порт на хосте |
|---|---|---|
| `n8n` (2.42.7) | оркестрация workflow | 5678 |
| `mcp-github` | GitHub MCP (чтение PR и файлов) за supergateway | нет (только сеть compose) |
| `mcp-fs` | Filesystem MCP с каталогом `legal-docs` (read-only) | нет |
| `semgrep-runner` | маленький сервис на Go: клонирует коммит PR и запускает semgrep с правилами из `rules/pd-leaks.yml` | нет |
| `prometheus`, `grafana` | мониторинг (Часть 4) | 127.0.0.1:9090, 127.0.0.1:3000 |

Тестовый проект с «чужим» кодом: репозиторий `rehab-backend` (ветка `main` и ветка `feature/pain-diary`, из которой открывается PR с нарочно заложенными проблемами). Юридические документы-моки лежат в `stand/legal-docs/`.

### Как запустить

1. Нужны Docker с Compose и доступ в интернет (VPN при необходимости: образы, GitHub, OpenRouter)
2. `cp .env.example .env` и заполнить: версии образов, `N8N_ENCRYPTION_KEY` (`openssl rand -hex 32`), `GITHUB_MCP_TOKEN` (fine-grained токен только на чтение: Contents и Pull requests), пароль Grafana
3. `docker compose up -d --build`
4. В n8n (`http://localhost:5678`): создать credentials — **GitHub API** (fine-grained токен с правом записи: Pull requests, Issues, Commit statuses; им публикуются комментарий, метки и статус) и **OpenRouter** (ключ). Импортировать [`pd-guard-workflow.json`](./pd-guard-workflow.json), выбрать credentials в нодах и опубликовать workflow
5. Сделать n8n доступным для GitHub: у стенда нет публичного адреса, поэтому использовался туннель pinggy (`ssh -p 443 -R0:localhost:5678 a.pinggy.io` бесплатный адрес живёт около часа). В репозитории `rehab-backend`: Settings → Webhooks → Payload URL `https://<адрес-туннеля>/webhook/github-pr`, Content type `application/json`, событие **Pull requests**
6. Открыть PR в `main`. В n8n на вкладке Executions появится выполнение, в PR комментарий, метка и статус `pd-guard`

Модель для агентов: бесплатная `nvidia/nemotron-3-super-120b-a12b:free` через OpenRouter, температура 0.1. Бесплатный лимит около 50 запросов в сутки, один прогон с двумя агентами тратит 10–20.

> Бюджет проекта: около 50 запросов в сутки. Один прогон Стража стоит 10–20. Пятый прогон за день — уже финансовый кризис, а шестой — реструктуризация долга перед OpenRouter.

**Наблюдения.**

### Что не получилось сделать «как в проде» (и как обошли)

- **Блок мержа.** Статус `pending` отображается в PR, но кнопку merge не блокирует: репозиторий приватный, а защита ветки с обязательными проверками на бесплатном тарифе GitHub для приватных репозиториев не применяется
- **Список файлов PR** берётся без постраничной выборки (первые 100 файлов)
- **Комментарий** при каждом новом пуше публикуется заново, а не обновляется
- **Туннель.** Cloudflare Tunnel из этой сети не заработал, использовался pinggy. Адрес бесплатного туннеля временный; в боевой системе вебхук приходит на постоянный адрес

Также пришлось несколько ограничить изначальный полет фантазии. Это были сознательное упрощение воркфлоу и использование временных инструментов, чтобы просто не усложнять учебную задачку слишком сильно. Ведь задача была показать именно настройку и работу системы 

## Часть 4 — Мониторинг

Инструмент: **Prometheus + Grafana**. Удобно, что n8n сам отдаёт метрики в формате Prometheus (`N8N_METRICS=true`, эндпоинт `/metrics`). Prometheus опрашивает его каждые 15 секунд, источник данных и дашборд в Grafana создаются из файлов (provisioning), стенд поднимается одной командой.

Дашборд «Страж ПДн: n8n» ([`stand/monitoring/grafana/pd-guard-dashboard.json`](./stand/monitoring/grafana/pd-guard-dashboard.json)). Метрики выбраны: жив ли процесс, не ломается ли он, не кончается ли ресурс, который его ограничивает (лимиты модели по токенам).

| Панель | Метрика | Что показывает |
|---|---|---|
| Активные workflow | `n8n_active_workflow_count` | опубликован ли workflow (при 0 вебхуки уходят в никуда) |
| Секунд с последней активности | `time() - n8n_last_activity` | приходят ли события вообще |
| Обращений к модели за 24 ч | `increase(n8n_ai_llm_generated_total[24h])` | сколько бесплатной квоты израсходовано |
| Доля ошибок за 1 ч | `n8n_workflow_failed_total / n8n_workflow_started_total` | ломается ли процесс |
| Выполнения по статусу | `n8n_workflow_execution_duration_seconds_count` по `status` и `mode` | поток PR, успехи и ошибки (webhook — настоящие события, manual — ручные запуски) |
| Длительность p50 / p95 | `histogram_quantile` по `n8n_workflow_execution_duration_seconds_bucket` | сколько проверка занимает у агентов |
| Обращения к модели в час | `increase(n8n_ai_llm_generated_total[1h])` | скорость расхода квоты |
| Память n8n | `n8n_process_resident_memory_bytes` | запас ресурсов на 2 vCPU |
| Задержка event loop, p99 | `n8n_nodejs_eventloop_lag_p99_seconds` | n8n не задыхается |

### Три метрики, по которым построил бы алерты

![Настроить алерты, нее](mem/drake.png)

Правила алертов не настраивались, но вот что я бы взял:

1. **Доля неуспешных выполнений за час.** `sum(increase(n8n_workflow_failed_total[1h])) / sum(increase(n8n_workflow_started_total[1h])) > 0.3` при условии, что неуспешных не меньше двух. Это единственная метрика, которая ловит поломку всей цепочки сразу. Условие «не меньше двух» нужно потому, что при малом потоке PR одна ошибка из двух запусков даёт 50 % и срабатывала бы на каждый одиночный сбой. Единственное нужно решать по периоду, для некоторых ситуаций часа может быть слишком мало из-за достаточно редких реквестов
2. **Обращения к модели за сутки.** `sum(increase(n8n_ai_llm_generated_total[24h])) > 40`. Бесплатный лимит модели около 50 запросов в сутки, а один прогон тратит 10–20. Когда лимит кончится, проверки PR остановятся молча (агент вернёт ошибку `429`), а это главный ограничитель всей системы
3. **p95 длительности выполнения.** `histogram_quantile(0.95, sum by (le) (rate(n8n_workflow_execution_duration_seconds_bucket{status="success"}[1h]))) > 360`. Обычный прогон занимает от одной до четырёх минут, в основном это время агентов. Рост за шесть минут означает, что агент зациклился на вызовах инструментов или модель отвечает слишком медленно

> Алерты в этом стенде идеальны: за всё время они ни разу не разбудили дежурного, потому что дежурный — это я, а в 3 часа ночи я сплю.

> P.S. Ни один пациент при написании отчёта не пострадал: весь «медицинский» код — мок, а настоящих персональных данных в репозитории меньше, чем в среднем резюме. Любые совпадения с реальными проектами случайны и автор не несет за них ответственности😁
