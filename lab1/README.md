## Часть 5 — Свой докер скрипт

Здесь объединяем все предыдущие шаги в один общий скрипт: [`mydocker.sh`](./mydocker.sh)

Структура:
- Создание cgroup `mydocker` с лимитами (200mb памяти, 50% cpu, 50 процессов максимум).
- Кладем shell, от которого запускаем api, в cgroup, чтобы избежать race condition — созданный api сразу попадает в нужный cgroup как дочерний процесс shell.
- Изолируем все неймспейсы через unshare (pid, uts, ipc, user, net, mount).
- Ограничиваем права через setpriv (делаем полный сброс capabilities).
- Запуск seccomp-обертки с фильтрами для сервиса.

![Успешный запуск mydocker.sh](screenshots/20.png)

Теперь сравним это с запуском `docker run`:
```bash
docker run --rm --name api-docker \
  --memory=200m --cpus=0.5 --pids-limit=50 \
  --cap-drop=ALL --security-opt no-new-privileges \
  -p 8080:8080 \
  -v "$PWD/api/api":/api:ro \
  debian:bookworm-slim /api
```

Docker сам создал PID namespace, изолирует сеть и пробрасывает наружу порт для доступа к сервису внутри контейнера, устанавливает лимиты.

| | mydocker.sh (свой) | docker run |
|---|---|---|
| Namespaces (pid/mount/uts/ipc/net/user) | Настраивали вручную через `unshare`, каждый флаг явно | То же самое из коробки, автоматически |
| Сеть | `--net` даёт ПУСТУЮ сеть, `/health` снаружи НЕ отвечает без `nsenter` (сами не строили мост) | Docker сам поднимает bridge-сеть (`docker0`), NAT и проброс порта (`-p 8080:8080`) — `curl localhost:8080` работает сразу, без доп. инструментов |
| Capabilities | Урезали вручную через `setpriv --bounding-set=-all` | Docker по умолчанию УЖЕ убирает большую часть опасных capabilities (не даёт полный root-набор, как голый `sudo`), можно тонко настроить через `--cap-drop`/`--cap-add` |
| Seccomp | Писали свой C-код с libseccomp, оборачивали `exec()` | Docker применяет seccomp-профиль ПО УМОЛЧАНИЮ (default profile, блокирует ~44 опасных syscall) без каких-либо действий с нашей стороны; свой профиль подключается через `--security-opt seccomp=profile.json` |
| Файловая система | Использовали `chroot /` — то есть ФС ХОСТА напрямую (не изолированная ФС, никакого образа) | Даже без своего Dockerfile — базовый образ `debian:bookworm-slim` (Union FS) |
| Настройка лимитов | Вручную: `mkdir` cgroup, `echo ... > memory.max/cpu.max/pids.max`, ручное перемещение процесса в cgroup ДО запуска (иначе race condition) | Прямые флаги: `--memory`, `--cpus`, `--pids-limit` — Docker сам создаёт cgroup и настраивает лимиты, без единой ручной команды с `/sys/fs/cgroup` |
| Управление жизненным циклом | `kill <PID>` вручную, нет единого способа "остановить/удалить" | `docker stop`/`docker rm`, единый интерфейс управления, логирование (`docker logs`), рестарт-политики |
| Простота использования | Много ручных шагов, легко забыть флаг или столкнуться с race condition | Одна команда `docker run` с флагами, вся сложность скрыта |

**Вывод**

Docker под капотом вызывает те же механизмы, что использовались по ходу работы, но для конечного пользователя делает это максимально удобным, чтобы избежать заморочек: сам добавляет изолированную ФС, сам делает сетевой мост для доступа снаружи вместо настройки пустого `--net`, и делает это синтаксически чуть проще.

## Часть 7 — Гипервизор

Ну а тут мы идем на уровень глубже и смотрим на gVisor (`runsc`) — это песочница, которая ставится вместо обычного `runc` рантайма в докере и подменяет собой часть работы с ядром.

Ставим `runsc`, регистрируем его как рантайм в докере (`runsc install` сам правит `/etc/docker/daemon.json`) и перезапускаем демон. Дефолтным рантаймом всё ещё остаётся `runc`, `runsc` просто становится доступен как опция через `--runtime=runsc`.

Запускаем наш образ под gVisor:
```bash
docker run -d --runtime=runsc --name api-gvisor -p 8080:8080 api:latest
```

`/health` отвечает `ok` как ни в чём не бывало — то есть сервису вообще всё равно, под каким рантаймом его подняли, разницу видно только "изнутри".

А теперь самое интересное — спрашиваем у контейнеров, какое у них ядро:

![uname -a под gVisor и под обычным runc](screenshots/25.png)

Под gVisor `uname -a` выдает `4.19.0-gvisor` — это вообще выдуманная версия ядра, которой не существует на хосте. А если тот же самый образ запустить обычным `docker run` (без `--runtime`), `uname -a` покажет настоящее ядро хоста (тот же `6.8.0-...generic`, что и на самой VM).

Смысл в том, что под `runc` контейнер дергает syscalls напрямую в настоящее ядро хоста — namespaces/cgroups/capabilities/seccomp лишь ограничивают, что ему видно и что можно делать, но ядро одно на всех, со всеми его потенциальными багами. А под `runsc` между контейнером и реальным ядром сидит отдельный userspace-процесс `sentry`, который сам реализует урезанный набор Linux-синтаксисов — грубо говоря, "притворяется ядром". Поэтому `uname` внутри отвечает не настоящее ядро, а sentry — он и подсовывает выдуманную версию. Если в реальном ядре есть syscall-баг, контейнер под gVisor до него просто не дотянется напрямую, потому что общается не с ядром, а с прослойкой.

**Что все равно остается общим с хостом**

Даже под gVisor контейнеры на одной машине всё ещё сидят на одном физическом железе (CPU, память, диск) и в конечном счете на одном хостовом ядре — sentry сам не может выполнять вообще всё сам с нуля, часть операций он всё равно проксирует в реальное ядро (через ограниченный интерфейс, обычно ptrace или KVM). Главное ограничение в том, что контейнер — это не полноценная виртуалка со своим собственным ядром: он либо делит ядро хоста напрямую (runc), либо частично прикрывается прослойкой (gVisor), но в обоих случаях граница слабее, чем у настоящей VM с hardware-виртуализацией (VT-x/AMD-V). Поэтому там, где нужна прямо серьезная изоляция, берут что-то посерьезнее — Kata Containers или полноценные VM, а не только gVisor.

Сделаем дашборд для сбора нужных метрик. Собирать будем:
- **Memory Usage**: `container_memory_usage_bytes{name="api-monitored"}`. Чтобы мониторить скачки по потреблению и отлавливать приближение OOM, когда сервис может упасть по памяти.
- **CPU Usage**: `rate(container_cpu_usage_seconds_total{name="api-monitored"}[1m])`. Мониторим текущую нагрузку на CPU, чтобы понимать, насколько сервис вообще переваривает нагрузку, и вовремя поймать момент, когда процессора скоро перестанет хватать, допустим, на количество пользователей в моменте.
- **CPU Throttling**: `rate(container_cpu_cfs_throttled_seconds_total{name="api-monitored"}[1m])`. Смотрим на показатель троттлинга процессора, чтобы понимать нехватку процессорного времени относительно реальной нагрузки и избежать момента, когда сервис "как живой, но не живой" и работает с неохотой.

![Дашборд с тремя панелями](screenshots/27.png)
